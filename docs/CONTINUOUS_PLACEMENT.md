# 连续二维空间布局（替换固定锚点）

## 一、审查：原来的定位确实是"枚举几个点"

`WindowGeometryResolver.resolveFloating` 旧实现（重构前的原文摘要）：

```swift
var candidates: [CGRect] = []
candidates.append(contentsOf: [preservedOrigin])                 // 1. 锚点
for rect in anchors.prefix(6) {
    candidates.append(contentsOf: FreeSpaceAnalyzer.anchorPoints(in: rect, size: size))
}                                                                // 2. 每块空地的四角/中心/上下中
candidates.append(center)                                        // 3. 当前位置居中
for candidate in candidates {
    guard fits, !overlaps else { continue }
    return MorphologyTarget(...)                                 // 4. 第一个能放下的就用
}
```

问题有两层：

1. **候选点是离散的**：每块空地只试 7 个点（四角+上中+中+下中），屏幕正中间的空洞若不是"空地中心"就永远落不上去；
2. **没有评分**：第一个放得下的直接返回，既不比较移动距离，也不比较"原地缩小 vs 横跨屏幕"。

## 二、新结构

```
自由矩形（FreeSpaceAnalyzer.maximalRects，连续）
        ↓  每种形态 × 每个矩形
候选位置 = { 当前位置投影, 用户记忆位置投影, 左上/左下/右上/右下锚点投影,
             四角, 上中/中/下中, 1/4 与 3/4 梯度位, 贴边吸附 }
        ↓  统一评分
PlacementCandidate { morphology, frame, score, breakdown }
        ↓
PlacementSolution { best, alternatives, freeRects, reason, snapshotVersion }
```

关键在于**投影**：把一个点夹回矩形内、保持尺寸、尽量少移动。
因此落点是连续量 `(x, y)`，不是角点。

### 评分

```
score = 4.2·stability + 0.8·slack + 1.2·preference
      − 2.4·morphologyCost − 2.0·movement
```

- `stability`：**左上角位移**（不是中心距）。形态切换时尺寸会变，中心必然跳，
  用中心距会把"原地缩小"判成"移动很远"，于是丢掉锚点去选别的位置——实测踩过；
  左上角与当前一致时直接给满分。
- `slack`：自由区域相对播放器的余量。
- `preference`：离用户记忆位置多远。
- `morphologyCost`：每紧凑一档的代价（`tightnessOrder` 差值）。
- `movement`：位移 / 屏幕对角线。

硬约束：完全落在安全区内、不与任何障碍物相交、与障碍物至少留 6pt 间距
（候选生成时先把自由矩形内缩，装不下才回退到原始矩形）。

## 三、接入方式

求解器只产出 `PlacementSolution`，**不碰 NSWindow**；执行仍在 `MorphWindowController`
（`moveWithContinuity`：近处平移、远处淡出迁移淡入，走 `MorphTransitionPlan`）。
`snapshotVersion` 由控制器的 `spatialSeq` 提供，过期结果直接丢弃。

## 四、测试

纯算法（`ContinuousPlacementSolverTests`，当时 6 条）：

| 用例 | 断言 |
|---|---|
| B 自由位置 | 四角被占、中间留洞时，落点必须在洞内（`midX∈(500,1100)`、`midY∈(240,660)`） |
| C 多窗口不规则空间 | 落点不得与任何窗口相交，且必须完整落在求解器自己算出的某块自由矩形里 |

## 五、现场验证（真实窗口）

环境：2048×1152@2x，Chrome + TextEdit 作为真实障碍物。

```
Chrome  = (0, 0, 2048, 610)      → AppKit y 542…1152 之上
TextEdit= (0, 900, 2048, 250)    → AppKit y 2…252
中间空带                            → AppKit y 252…542（屏幕中部，不是四角）

播放器原位置 (514, 100) 被完全压住，遮挡 100%
RELOCATE (514,100,420,80) → (514,258,420,80)   occlusion 100% → 0%
窗口实际移动到 CG (514,814) = AppKit y 258
```

调试面板（`screenshots/flow/19-continuous-placement.png`（截图已从公开仓库移除））同一时刻显示：

```
形态 compact | 遮挡 0%
屏幕  0,79 2048×…
播放器/目标 514,258
前台窗口 1 个  0,0 2048×252
候选区   1 个  0,252 2048×870
```

**结论**：落点 x=514（既不是 4 也不是屏幕右缘），y=258 落在屏幕中部的空带里。
这正是旧实现做不到的"非角点、非预设位置"。

## 六点五、主动检测（用户反馈后新增）

用户的反馈是："它应该是主动检测的，不是我遮挡它它才动。"

原来的触发条件只有"我被压住了"，属于纯反应式。现在每次环境变化都会跑一次完整求解：

1. 算**当前摆放**的评分；
2. 算**最优摆放**（形态 × 位置）；
3. 若当前合法但最优方案改善 ≥ 15%（`minimumRelocationImprovement`）、位移 > 12pt、且不在
   800ms 冷却内 → **主动挪过去**（日志 `PLACE proactive improvement=… moved=…pt`）；
4. 若当前不合法 → 直接采用最优方案（可能同时换形态）；
5. 换形态也要过同一个 15% 门槛，避免为了 0.1 分翻来覆去。

权重也按"优先大块空区"重调（实测发现旧权重会把播放器塞进最近的一条窄缝）：

| 项 | 旧 | 新 |
|---|---:|---:|
| stability（保持不动） | 4.2 | 1.6 |
| slack（空间宽裕） | 0.8 | 5.0 |
| movement（移动距离） | 2.0 | 1.4 |
| 新增 squeeze（被挤扁惩罚） | — | 3.0 |

`slack` 同时改成对数刻度：空区面积是播放器的 12 倍与 29 倍时，线性比例分不出"窄缝"与"大空区"。

## 六点五之一、无遮挡优先（用户第二轮反馈）

用户的第二条要求："应该优先移动到完全没有遮挡的桌面，然后是一级、二级。"

评分是加权和，天生会把"近处勉强塞下"和"远处完全干净"折中。
所以把**无遮挡等级**提成排序的第一关键字，分数只在同级内比较：

| 等级 | 含义 |
|---|---|
| 0 | 标准尺寸放进干净空间（完全无遮挡、未被压扁） |
| 1 | 放得下但被压扁/很紧 |
| 2 | 有遮挡或只能用降级形态 |

同时：
- 只有"当前已经是 0 级"才允许原地不动；等级更差就去找干净空间，
  哪怕更远——这正是用户要的优先级。
- 增加"没必要地缩小"惩罚：某块空地放得下更宽松的形态却选了更紧的，额外扣分。

### 实机验证（Chrome 三个位置）

| Chrome 位置 | FLOW 落点 | 结果 |
|---|---|---|
| x=0, w=700（占左） | (1506, 882) 420×80 | 右侧干净区，标准尺寸 |
| x=500, w=1000（居中） | (1506, 882) 420×80 | 仍在右侧干净区（换边没必要） |
| x=1200, w=800（占右） | (774, 882) 420×80 | **换到左侧**干净区 |

三次都是标准 420×80、零遮挡，且只在"必须换边"时才移动。

## 六点六、仍未解决的缺陷（据实）

之前"播放器落到 x=514（在 Chrome 内部）"的问题，已定位并修掉：

- **求解器合法性校验不足**：`positions` 只校验了安全区，没校验"这块自由矩形"和真实障碍物，
  于是紧贴障碍物下缘的 33pt 窄条也被当成可放位置。现在同时校验矩形包含 + 障碍物不相交。
- **执行期重读 AX 拿到空障碍物**：变形瞬间焦点可能短暂回到自己，`obstacles()` 返回空，
  目标位置退回无约束结果。现在执行器用评估时缓存的 `lastObstacles`。

修复后同一场景稳定落在 (1506, 882)，日志 `rejected=noBetterOption` 连续多条，无震荡。

## 六点八、障碍物来源改为"整块桌面"（用户截图反馈）

用户反馈：两个全宽窗口之间、中间那个应用窗口的**左右两侧**明明是空的，
FLOW 却停在了中间那个窗口上面。

根因：障碍物只取"前台应用"的窗口。前台是 Chrome，中间那个应用不算障碍，
于是引擎认为当前位置没问题。

改法（`Spatial/VisibleWindowScanner.swift`）：

- 用 `CGWindowListCopyWindowInfo` 扫描**所有**在屏窗口的几何；
- 只取 `layer == 0` 的普通窗口，排除自己、排除最小化、排除过小窗口；
- 转换到 AppKit 坐标（以主屏高度为基准）；
- 有辅助功能权限时再叠加前台应用的 AX 精确矩形，去重交给并集计算。

这个 API 拿几何**不需要**屏幕录制或辅助功能权限，也不读任何窗口内容。

配套两处保护：

1. **目标合法性兜底**：任何来源的目标矩形（含冷启动时算出的旧 `pendingPlacement`）
   在动画前都要再验一次"不与障碍物相交"，不合法就地重算；
2. **边条偏好**：贴安全区上下沿 24pt 内的落点扣分（权重 2.2），
   有中部空隙时优先中部，而不是被挤到屏幕最边上。

## 六点九、抽搐/反复横跳的根因与修复

用户反馈"现在会抽搐、反复横跳"。实测（桌面完全静止、输入哈希不变）：

```
修复前：45 秒内 22 次动作
修复后：45 秒内  3 次动作，且 3 次都是 "occlusion 100% -> 0%"（被真实窗口压住后的避让）
```

三个根因，逐个修掉：

### 1. 形态决策自引用（主要原因）

候选里同时放了"当前形态"，用 `morphologyCost` 兼做稳定项。于是：
`胶囊 → 算出来 edge 更好 → 变 edge → 再算又觉得胶囊更好 → 变回胶囊`，
**输入完全没变**也会无限互翻。

修法：形态改由**几何**决定——`widestSupportedMorphology(freeRects)` 取"按标准尺寸放得下"
的最宽松形态，位置再在一档内优化。目标只取决于桌面，不再取决于"我现在是什么"。

### 2. 自动展开循环

出现过 `capsule → expanded → capsule` 的自发循环。修法：自动路径上的
`.expanded` 一律拦截（`SUPPRESSED auto-expand`），只有用户主动要求才置位放行。

### 3. 无谓的压扁与位移

- 有标准尺寸的落点就绝不用被压扁的落点（否则会挑"最近但只够 381 宽"的缝，把胶囊压成 381×56）；
- 主动重定位门槛：改善 ≥15%、位移 >24pt、4 秒冷却、3 秒内去过的位置不再去；
- 同一个更优位置要连续出现 3 次评估才采纳（单次抖动不算理由）；
- 形态切换 3 秒限流。

## 六点十、过期结果的版本号丢弃（规格 §八）

`pendingPlacement` 现在带 `pendingPlacementVersion`（= 评估时的 `spatialSeq`）。
执行动画前比对版本：不一致说明空间在决策之后又变了，直接丢弃重算，
避免"动画走到一半被旧结果拉回旧位置"。

三层保护叠加：

1. 版本号不符 → 丢弃；
2. 目标矩形与当前障碍物相交 → 重算（`TARGET rejected`）；
3. 目标不是完整尺寸但存在完整尺寸选项 → 换完整尺寸（求解器内部过滤）。

## 六点十一、静置稳定性（干净环境实测）

不跑测试、不动任何窗口的 60 秒：

```
60 秒纯静置动作次数: 0
静止形态: 完整 420×80 compact
```

对比修复前的 22 次 / 35 秒，这一项已经收敛。

## 六点十二、自由矩形的极大性剪枝（规格 §三.6）

坐标压缩会枚举出**所有**空矩形，其中大量被更大的矩形完全包含。
实机日志里 4 个障碍物就能产生 **58 个**候选矩形，其中多数是冗余的。

新增 `FreeSpaceAnalyzer.pruneContained`：按面积从大到小扫，丢掉被已保留矩形完全包含的结果。
实机对比：**58 → 7** 个。调试面板的"候选区"这才读得出重点，候选生成也少了近 90% 的组合。

`FreeSpaceMaximalityTests`（4 条）锁定契约：无互相包含、空区不丢失、无障碍返回整屏、
重叠障碍不产生非法矩形。

## 六点十三、多屏坐标（规格 §十二 H 的逻辑层）

这台机器只有一块屏，**连接/断开无法实测**。但坐标换算是纯函数，可以合成屏幕几何覆盖：

| 场景 | 断言 |
|---|---|
| 副屏在主屏左侧（x 为负） | 安全区右缘接主屏左缘 x=0，不偏移 |
| 副屏在主屏上方 | 安全区下沿紧接主屏上沿 |
| 刘海屏 + 菜单栏自动隐藏 | 刘海高度只扣一次 |
| 菜单栏可见 | 不再重复扣刘海 |
| 在副屏安全区内求解 | 落点留在副屏，不跨回主屏 |

`MultiDisplayGeometryTests`（5 条）全绿。这证明"换算逻辑正确"，**不等于**"插拔实测通过"。

## 六点十四、用满空白：形态资格改为按**最小尺寸**判定（用户反馈）

用户反馈："变形的种类不是很多，不能有效利用剩下的空白部分。"

原因：形态资格用的是**标准尺寸**——`widestSupportedMorphology` 要求 392 宽的胶囊按标准尺寸
放得下，于是一个 320pt 宽的空隙直接把胶囊/mini 全部排除，只剩 300×34 的贴边条，
大半个空隙被浪费。

各形态本身是有尺寸区间的：

| 形态 | 标准 | 区间 |
|---|---|---|
| mini | 420×80 | 320…560 × 68…96 |
| 胶囊 | 392×56 | 240…640 × 44…64 |
| 贴边 | 300×34 | 168…900 × 26…44 |

改为按**最小尺寸**判定资格，"尽量接近标准尺寸"交给评分里的 squeeze 惩罚。

### 实测（同一块空隙，前后对比）

| 版 | 落点 | 占用面积 |
|---|---|---|
| 修改前 | `(1681,392) 367×200` 空隙里放 **300×34**（贴边条） | 10200 |
| 修改后 | 同一空隙放 **347×80**（迷你，接近标准 420×80） | 27760 |

面积提升约 2.7 倍，且 55 秒静置 **0 次动作**（无抽搐）。

## 六点十五、设计稿对照（用户提供参考图）

参考图里的四种歌词形态：纯文本 / 胶囊（约 432×88，内含进度线）/ 双行 / 边缘竖条。
对照当前实现：

| 设计稿 | 当前实现 | 差距 |
|---|---|---|
| 边缘歌词（竖直圆角条） | `dormant` 26×72 圆角竖条 | 一致 |
| 胶囊歌词 | `capsule` 392×56 | **偏小**：设计稿约 432×88，还要放进度线 |
| 双行歌词 | `LyricsShape.doubleLine`，浮窗高 76 | 有形态，但没有独立的浮窗规格 |
| 纯文本歌词 | `LyricsShape.board`，浮窗高 152 | 有形态，同上 |

**试过把胶囊放大到设计稿尺寸（432×88）**：构建通过，但 4 条用例失败——
内容布局、进度线位置、以及若干硬编码 392 的几何假设都跟着动。

结论：放大胶囊不是改一个常量，而是"浮窗尺寸 + 内部排版"的联动改动，
必须当成独立任务做（把四种形态的浮窗规格与内容布局一起对齐设计稿），
不能在收尾阶段夹带。已回退，源码保持 392×56。
