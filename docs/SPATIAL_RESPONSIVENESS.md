# 变形与遮挡响应优化 · 2026-11-14

## 问题与修复

1. **主线程重复计算**：一次空间评估里，引擎、当前评分、形态候选、最终求解、调试叠加层分别计算自由矩形。旧算法枚举四条边并逐个检查障碍，接近 O(n⁵)。
   - 自由空间改成 x 区间扫描 + y 障碍并集补集，约 O(n³ log n)，仍保留精确极大矩形。
   - `AdaptivePlacementPlanner` 在后台单飞计算一次空间，统一输出形态与落点，调试界面复用结果。
   - 结果回主线程后校验版本、窗口矩形、当前形态及锁定/隐藏状态，过期结果丢弃并重算最新快照。
2. **连续拖动饿死评估**：旧 trailing debounce 每次通知重置 100ms。
   - 改为固定 80ms 合并窗口，后续事件更新版本但不延后截止时间。
   - AX 监听具体窗口的移动/缩放/关闭/最小化，在 common run-loop modes 下接收；AX 只发事件，不在几何热路径同步查询外部应用属性。
3. **防抖叠加导致迟钝**：3 秒形态锁、4 秒位置锁、三次候选 streak、桌面几何签名锁与状态机冷却互相覆盖；实际执行还可能重新选址。
   - 去掉控制器叠加门槛；统一状态机冷却与恢复稳定期。
   - 使用同次快照落点，不再让三个算法互相推翻。优先保持当前位置；受遮挡时让位，内容收益明显且空位稳定时也可主动舒展或迁移，不再仅在被挡住时动作。
4. **空位释放后不恢复**：冷却结束缺少唤醒；缓存只记非空障碍物，旧窗口永久残留。
   - 明确计算下一次评估 deadline，主动安排重试，不依赖下一次窗口事件。
   - 空障碍集合是有效快照。复用播放 tick 做几何补查，只有几何变化才求解，覆盖完整窗口与把手。
5. **首次变形停顿**：壁纸在主线程完整解码，第一轮真实评估含窗口操作最高 123.87ms。
   - 改为后台 ImageIO 缩略采样，结果回主线程更新外观。
6. **相关正确性**：副屏 CG 坐标按主屏原点转换；障碍物裁剪、去重与稳定排序；用户拖播放器时暂停自动布局；旧移动淡出任务可取消；显式隐藏始终下屏，自动收缩仍按把手偏好。
7. **2026-11-22 冷启动检测与自动避让可靠性加固**：
   - **冷启动首帧预热与恢复守卫**：`start()` 非阻塞调用 `warmUpObstacles()` 与偏好读取并行预热快照；`restorePreferences()` 增加 `userIntentSeq` 守卫避免异步恢复覆盖用户刚切换的形态，并在恢复为悬浮态时携带实时障碍物快照求解初始无遮挡位置。
   - **前台悬浮态巡检与冲突自愈**：`compensatingCheck()` 在 `!isAppActive || machine.state.current != .expanded` 时均生效（刚打开或刚切到悬浮尚未离开本应用时照常巡检），且当悬浮窗仍与障碍物冲突又尚未针对当前 `(frame, morphology, obstacles)` 完成避让尝试时主动唤醒重算。
   - **6 秒保护期内受遮挡即时同形态让位**：`performEvaluation()` 将受遮挡紧急让位（`displaced`）与主动舒展（`opportunityReady`）彻底解耦，`displaced` 不受 `userMorphUntil`（6 秒保持期）及 `opportunityGate`（500ms 稳定门）阻拦，并通过 `resolveSameMorphologyTarget` 在跨形态建议或形态锁定时兜底求解同形态无遮挡落点。
   - **外部几何通知防饥饿与看门狗收尾**：`evaluateSpace(immediate:geometryOnly:)` 仅在自身状态或用户意图改变（`!geometryOnly`）时推进 `spatialSeq`，外部拖窗事件在评估在飞时只置 `evaluationRequested = true` 排队补算；动画期间挂起 `deferredEvaluationPending`，并修复 `animateFrame` 看门狗在坐标已到位时早退导致 `isAnimatingGeometry` 永久挂死的缺陷（由 `AutoAvoidanceReliabilityTests` 6 项单测覆盖）。

## 当前行为

- 完整播放器正在前台使用时不自动收缩，也不自行避让。
- 用户已使用播放器并切走后，根据空间自动缩成迷你/胶囊/贴边。
- 没有可容纳的空位时收成边缘把手（默认）；空间恢复后自动恢复可容纳的悬浮形态，不自动打开完整播放器。
- 用户点击展开仍是最高优先级；形态锁限制变形，位置锁暂停自动布局；显式隐藏与系统挂起不参与恢复。
- 用户指定形态/歌词排布后保留 1500ms 保持期；之后恢复空间自适应。
- 空白较宽时可舒展到 640×240 的迷你歌词卡；较窄但较高时使用最高 200pt 的歌词板；细横带使用宽胶囊。达到内容上限即停止增长，不填满整个桌面。
- 当前落点合法但内容明显受限时，可迁往更合适的空白；同形态主动优化需候选稳定 500ms，受遮挡的让位不额外等待这道门槛。

## 第二轮：主动利用桌面空白

用户追加反馈“还不能很好地利用空白桌面空间”。原因不是没识别到空白，而是：

1. 旧求解器当前合法就提前返回，只生成标准尺寸；大空区里的 420×80 与窄缝里的 420×80 没有内容差别。
2. 用“空区面积 / 候选面积”奖励余量，会反向鼓励播放器越小越好。
3. 即便窗口增高，原来的单行内容没有随高度增加信息。

当前修复：

- 自动模式枚举宽度与内容高度档位：迷你 80/112/168/240pt、胶囊 56/76/152/200pt；只生成完全落在自由矩形内且不碰障碍物的候选。
- 空区容量独立计分，歌词/控制信息收益单独加分；手动切换、形态锁与保持期继续使用标准尺寸路径。
- 合法旧落点也参与比较；收益至少 0.65 分且达到积极度比例门槛，并有明显尺寸/位置变化，才考虑同形态优化。候选持续 500ms 才执行，2pt 几何变化不会重新跳位。
- 迷你增高后显示更大封面、歌词上下文；胶囊根据实际高度使用单行、双行、歌词板视图，不覆盖用户保存的排布偏好。
- 截图复核发现歌词板的强调竖线被自由 HStack 撑满高度，已改为当前歌词的 overlay；上下文居中排布，空闲态有可操作提示，不再拉长空装饰。像素回归检查单行强调线高度小于 50pt。

实机几何证据（1920×1080 桌面，两块外部窗口）：

```text
free=(1592,89,318,503)
restored capsule=(1520,526,392,56)
target capsule=(1592,382,318,200)
下一轮 target=(1592,382,318,200)，移动 0pt
TIMING eval=5.02ms / 9.54ms
```

318pt 窄列低于迷你最小宽度 320pt，仍可利用纵向空白变成歌词板，而不是永远停在 56pt 单行。后续真实桌面被其他应用占满时，也观察到正常收成右边把手；这些是场景采样，不是完整输入延迟或长时稳定性跑分。

[歌词板内容渲染复核](<screenshots/space-use/narrow-gap-board-render.png>) 来自 SwiftUI `ImageRenderer`，只含控件自身，不是实机桌面截图；实机落点由上面的运行日志验证。AX 路径、双屏和真鼠标首击的未验证项仍如前述。

## 第三轮：移动与躲避的卡顿（2026-11-15）

用户反馈"过渡有点卡，就是卡片移动、躲避的时候"。这次先用独立进程采样窗口矩形，
把"卡"量化：记录播放器窗口每次位置变化之间的间隔。

### 定位到的两个真因

1. **远距离躲避是硬跳，不是移动。**
   旧 `moveWithContinuity` 在距离超过屏幕对角线 32% 时走"淡出 80ms → 瞬间 setFrame → 淡入 120ms"。
   实测一次 `RELOCATE from=(10,984,392,56) to=(1584,931,326,76)`（横跨 1575pt）只采到 **1 帧**。
   用户看到的是卡片凭空跳走，观感上就是"卡了一下"。
2. **主线程在同步枚举 WindowServer。**
   `CGWindowListCopyWindowInfo` 中位 **0.30ms** 但峰值 **53.47ms**；
   `NSWorkspace` 壁纸接口中位 0.45ms、峰值 7.6ms。而每个 tick 里 `compensatingCheck()`
   与 `updateBackgroundAppearance()` 各扫一遍，一帧预算只有 16.7ms。

### 修复

- `moveWithContinuity` 改为**始终连续插值**：时长按距离缩放（近 0.16s、最远 0.30s），
  不再有淡出瞬移分支。窗口是同一个，连续滑动才是"同一件东西在动"。
- 新增 `Spatial/ObstacleProvider.swift`：扫描放到后台（`Task.detached`），主线程只读缓存；
  同一时刻最多一次扫描在飞，重复请求合并；`ObstacleRefreshPolicy` 用 180ms 最小间隔限流。
  空间决策用 `await refreshedObstacles(...)`，动画路径用 `cachedObstacles(...)` 只读不等待。
- 壁纸判读复用同一份障碍物缓存，不再每个 tick 自己枚举一次。

### 实测（同一台机器，追踪窗口矩形）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 远距离躲避（1575pt） | 1 帧（瞬移） | **15 帧，13–22ms/帧** |
| 形态切换 capsule→edge | 9 帧、16–22ms | 7–9 帧、14–20ms（未受影响） |
| 主线程窗口枚举 | 每 tick 2 次、峰值 53ms | 0 次（后台 + 缓存） |

追踪方式：独立进程每 2ms 读一次 `CGWindowListCopyWindowInfo`，记录相邻两次位置变化的间隔；
用临时障碍窗口把播放器挤出原位来触发躲避。这是**窗口几何节奏**，不是 GPU 帧率或 Instruments 采样。

### 仍存在的边界

- 形态切换在**超远距离**（>32% 对角线）时仍沿用"淡出迁移淡入"，这是既有规则与测试约定的行为，
  本轮未改；实测常见的中近距离形态切换是连续的。
- 拖动窗口时的流畅度取决于系统对 `NSAnimationContext` 的调度，本轮只验证了程序触发的迁移。
- 未做 Instruments 帧率、能耗或长时间运行采样。

## 第四轮：动画流畅度（同日追加）

用户进一步反馈"动画很明显不到 20 帧"。补充三处改造：

1. **动画期间不再逐步同步重绘。**
   `animateFrame` 原来用 `setFrame(display: true)`，每推进一小步就要求同步绘制一次。
   改成 `display: false`，交由 WindowServer 合并到显示器刷新节拍。
2. **动画期间冻结排版尺寸。**
   窗口逐帧变尺寸时，内容若按实时尺寸排版，会在高度穿过 108/160/224pt 断点时
   整棵子树换掉（标题→歌词→上一行）。现在动画期间钉在目标尺寸，
   断点只在落地时生效一次；文字投影也在动画期间关闭（它需要逐帧离屏渲染）。
3. **迁移 = 先定尺寸再纯滑移。**
   `moveWithContinuity` 在起点一次性把尺寸设为目标值，之后只改变原点。
   实测滑移期间内容重排从"每帧一次"降到整段 **5 次**。
   代价是尺寸变化发生在动画起点（对常见的 392×56 → 326×76 这类小变化几乎不可见）。

另外确认了一个容易被忽视的事实：此前一直运行的是 **Debug 构建**，
SwiftUI 在未优化构建下的渲染开销明显更大。现在改用 Release 构建运行。

### 实测

| 指标 | 数值 |
|---|---|
| 躲避位移帧数 | 16 帧 |
| 位移帧间隔 | 7–23ms（多数 13–20ms） |
| 滑移期间内容重排 | 5 次（原为每帧 1 次） |
| Release 过渡重绘 | 中位 16.5ms、p90 19.9ms、≤20ms 占 91% |
| 屏幕录制复核 | 标称 56.3fps |

需要诚实说明：在窗口几何与宿主视图 `layout()` 两个维度上，我测到的都是接近 60Hz，
未能复现"不到 20 帧"的量化证据。用户的主观感受仍然有效，因此按上面前三条做了
结构性优化（减少重绘、消除逐帧重排、改用 Release），而不是只调时长。

## 第五轮：决策与动画彻底分离（同日追加）

用户提出的架构要求：**"算好最后落点，然后丝滑过去就行；动画不要影响下一次落点计算。"**
这一轮按这个原则重整了交接边界。

### 改动

1. **动画只负责呈现。** `animateFrame(frame:duration:finished:)` 接收决策层算好的落点，
   内部不重新求解、不读几何，因此动画过程不可能反向影响评估。
2. **收尾由动画真正落地驱动。** 原来过渡另有 `Task.sleep(plan.duration)` 定时器收尾；
   定时器一旦早于动画到达，`persistPlacement()` 就会把中间帧当成落点存下来。
   现在改为动画完成回调里收尾，并在收尾前**精确落回目标帧**。
3. **动画期间的中间帧不参与决策。** 补偿检查、窗口移动通知、壁纸判读都增加
   `isAnimatingGeometry` 守卫——中间帧的 `panel.frame` 不是任何人的落点。
4. **尺寸在起点定好，动画期间只动原点。** SwiftUI 内容因此完全不重排
   （实测滑移期间重排从每帧一次降到整段 5 次）。

### 尝试过但撤回的方案

曾用 `CADisplayLink` 自己逐帧驱动，想拿满显示器刷新。实测在本应用（非激活态面板）里
回调被系统节流到约 300ms 一次，反而更差，已撤回。现在仍用 AppKit 的
`NSAnimationContext`，但改为 `display: false` 由系统合并绘制，并把收尾逻辑搬到完成回调。

### 实测

| 项 | 数值 |
|---|---|
| 躲避位移帧数 | 17 帧 |
| 位移帧间隔 | 13–22ms |
| 落点精确性 | 收尾后 `distance=0`，窗口 frame 等于目标 |
| 反复切换漂移 | 5 次往返后尺寸不变 |

新增 5 条 `AnimationHandoffTests` 守卫这个契约：过渡结束不残留动画状态、落点精确、
反复切换不漂移、冻结尺寸只影响断点选择。

## 第六轮：修正"切换像闪过去"（同日追加）

用户反馈"感觉就是没做动画，切换都是直接闪过去"。用 4ms 间隔追踪窗口矩形，
确认这是**上一轮我自己引入的回归**：

```
327x240@10,720 → 300x34@10,926 → 300x34@10,828 → ...
```

尺寸**一步跳完**（327×240 直接变 300×34），只有位置在平移。原因是我为了减少重排，
把尺寸改成"动画起点一次性设定"。形态切换中最显眼的变化恰恰是尺寸，所以看起来就是闪。

### 修正

1. **尺寸改变时必须参与动画。** `presentationSizeOverride` 只用于*尺寸不变*的纯位置迁移；
   形态切换让尺寸跟位置由同一条曲线一起插值。
2. **去掉远距离的"淡出 + 瞬移 + 淡入"。**
   `plan.relocatesThroughFade` 仍保留在计划里（描述意图），但控制器不再据此跳过插值——
   `expanded↔capsule` 这类大跨度切换以前走的就是这条路，正是另一个"闪"的来源。
3. **零时长路径仍必须真的落位。** 移除瞬移分支时漏了这一条，
   导致"减少动态效果 / 测试"下窗口停在旧 frame；已补回并由此修好 5 条测试。

### 实测（4ms 采样窗口矩形）

| 切换 | 中间帧 |
|---|---|
| expanded → capsule | 11 |
| capsule → expanded | 14 |
| capsule → edge | 8 |
| edge → compact | 9 |

### 仍存在

`capsule → expanded` 中段有一次约 **87ms 的掉帧**（追踪里表现为一步跳很大）。
这是展开时重建完整播放器视图树（封面、列表、控制区）的主线程开销，
不是插值问题。后续可用"先动画后装配"或视图预热来削，本轮未做。

## 第七轮：适配所有刷新率（同日追加）

用户指出当前只有 60Hz 是虚拟显示器所致，目标是**适应所有刷新率**。

### 根因

原来时长写死在 0.16–0.30s。在 60Hz 上 0.18s 只有 11 帧——这就是"帧太少"。
而屏幕本身能出多少帧是硬件决定的（实测本机 `maxFPS=60`），软件无法凭空造帧。
能做的是：**同一段动画在任何屏幕上物理时长一致，帧数随刷新率自动增长。**

### 规则（`Morphology/MotionTiming.swift`）

```
实际时长 = max(基准时长, 最低帧数 / 刷新率)
```

- 最低位置数 **30**；零时长原样返回（"减少动态效果"与测试态必须保持瞬时）。
- 60Hz：0.18s → 抬到 0.50s，得到 30 个离散位置（原 18 帧时只有 0.30s）。
- 120Hz → 0.25s、144Hz → 0.208s、240Hz → 基准 0.18s 本身已够（43 个位置）。
  刷新率越高，凑够同样 30 个位置所需时间越短——这正是"高刷更丝滑"的来源。
- 刷新率两路来源：`NSScreen.maximumFramesPerSecond`，为空时回落
  `CGDisplayCopyDisplayMode.refreshRate`；都拿不到按 60Hz 估（宁可够帧）。
- 调试开关 `SLP_REFRESH_RATE=240` 可在任何屏幕上验证高刷路径的时长计算。

### 顺带修掉的两处主线程开销

1. 过渡结束的收尾（落库、重新评估）推迟一个 runloop：让最后一帧先提交到屏幕。
2. 删掉 `finishTransition` 里的整棵根视图重建——`model` 可观察，SwiftUI 自己会跟上。

### 实测（本机 60Hz 虚拟屏）

| 项 | 修复前 | 修复后 |
|---|---|---|
| 单次过渡位置数 | 9–11 | **28–30** |
| 应用内重绘间隔（中位） | 16.5ms | **16.0ms** |
| 录屏唯一画面（像素级） | — | 114/114，中位 16.7ms |
| >25ms 的重绘 | 有 | **0 次**（capsule→edge 全序列） |
| 展开过渡 | 曾有 87ms 空隙 | 中位 4.8ms，仅 2 帧略超 |

需要澄清一处测量陷阱：用 `CGWindowListCopyWindowInfo` 采样窗口矩形时，
缓动收尾阶段每帧位移不足 1px，坐标取整后会连续几帧"看起来没变"，
于是被误判成掉帧（曾误报 65ms）。以上结论以**应用内重绘间隔**为准。
